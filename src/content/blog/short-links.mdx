A URL shortener has a small public surface: accept a destination, return a short link, and redirect visitors. That makes it a useful project for exploring the decisions hidden behind a simple API.

## Validate the destination

Parse input with the platform’s URL parser. For a public link shortener, allow only the protocols the product supports.

```typescript
function parseDestination(input: string): string {
  const url = new URL(input)
  if (url.protocol !== 'https:' && url.protocol !== 'http:') {
    throw new Error('Use an HTTP or HTTPS URL')
  }
  if (url.username || url.password) {
    throw new Error('URLs must not contain credentials')
  }
  return url.href
}
```

Parsing a URL does not make its content trustworthy. Abuse reporting and rate limits are separate concerns. If the server later fetches destinations to generate previews, it also needs protection against requests to private networks.

## Let the database prevent collisions

A randomly generated short code can collide with an existing one. Put a unique constraint on the code, attempt the insert, and retry a bounded number of times when that specific constraint fails.

Checking whether a code exists before inserting is not sufficient: two requests can both observe an unused code and try to claim it at the same time.

## Keep redirects fast

The redirect path should perform one indexed lookup, verify that the link is active, and return the destination. A temporary redirect is useful when destinations can change; permanent redirects may be cached by browsers.

Do not wait for an analytics dashboard to update before redirecting the visitor. Send click events to a durable queue if tracking is required, and process them independently.

## Define what a click means

Bots, link previews, and retries can all visit a short link. A raw request count is not the same as a count of people.

Keep analytics labels honest, collect only the data you need, and make retention intentional. The redirect stays simple when everything around it has a clear job.
