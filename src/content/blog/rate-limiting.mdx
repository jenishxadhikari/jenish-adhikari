A rate limiter answers a simple question: should this request be allowed right now? The interesting part is deciding what “right now” means when traffic arrives in bursts.

A fixed window can allow twice its limit near a window boundary. A token bucket gives us a different tradeoff: a steady average rate, with room for short bursts.

## Think of requests as tokens

Imagine a bucket that holds ten tokens. Every request removes one. New tokens arrive at a constant rate, and the bucket never grows beyond its capacity.

- **Capacity** sets the largest burst you can accept.
- **Refill rate** sets the sustained number of requests per second.
- An empty bucket means the next request needs to wait.

> Capacity controls bursts. Refill controls throughput.

## A small implementation

This example tracks one bucket in one process. Injecting the time makes the behavior easy to test without waiting for a real clock.

```typescript
class TokenBucket {
  private tokens: number
  private updatedAt: number

  constructor(
    private capacity: number,
    private refillPerSecond: number,
    now = Date.now()
  ) {
    if (capacity < 1 || refillPerSecond <= 0) {
      throw new Error('Capacity must be at least 1 and refill must be positive')
    }
    this.tokens = capacity
    this.updatedAt = now
  }

  allow(now = Date.now()): boolean {
    const elapsed = Math.max(0, now - this.updatedAt) / 1000
    this.tokens = Math.min(this.capacity, this.tokens + elapsed * this.refillPerSecond)
    this.updatedAt = Math.max(this.updatedAt, now)
    if (this.tokens < 1) return false
    this.tokens -= 1
    return true
  }
}
```

With a capacity of ten and a refill rate of two, ten requests can pass immediately. After that, another request can pass every half second. Idle time fills the bucket again, but never beyond ten tokens.

## Where the simple version stops

An in-memory bucket belongs to one process. If an application runs on several servers, each server would have its own limit. A shared store and an atomic read–refill–consume operation are needed to enforce one limit across them.

Choose the bucket key carefully, too. An authenticated account is often a better key than an IP address shared by an office or a mobile network. Remove expired buckets so the limiter does not accumulate unused keys forever.

When rejecting an HTTP request, return `429 Too Many Requests` and communicate when the caller should retry. Rate limiting works best when clients can respond to it predictably.
